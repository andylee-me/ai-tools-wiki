程式碼精簡

/simplify

在你完成一段程式碼修改後執行。自動審查 git diff 或指定範圍內的變更， 找出重複邏輯、過度複雜的巢狀結構、可合併的函數，並直接提出精簡後的版本。 讓程式碼在功能不變的前提下，變得更易讀、更易維護。

適用時機

  • 完成一次功能開發或 bug 修復後，想確認改動沒有引入多餘的複雜度
  • 發現函數越寫越長、巢狀 if-else 層數越來越深時
  • 重構過程中，確認抽出的共用邏輯是否還能進一步合併
  • Code Review 前的自我檢查，讓提交的 diff 更乾淨
  • 接手舊有程式碼後，想快速找出可清理的技術債
  • 搭配 /code-reviewer 使用，在審查問題修正後再驗證精簡度

使用方式

  1. 完成程式碼修改
    先讓功能正確運作，確認測試通過後，再執行 /simplify。不要在功能還不完整時過早精簡。
  2. 執行 /simplify 並指定範圍
    可以不帶參數（自動分析 git diff），或指定特定檔案路徑、目錄，讓審查範圍更聚焦。
  3. 審查精簡建議
    Claude 會列出各項可精簡的位置，說明問題類型（重複邏輯、過深巢狀、可合併函數等）並附上精簡後的版本供比較。
  4. 確認並套用修正
    逐一確認每項建議，同意後讓 Claude 直接修改檔案；若有疑慮可個別跳過，保留原有設計決策。
  5. 重新執行測試
    套用精簡後再跑一次測試，確保行為沒有因重構而改變，接著提交。

使用範例

範例 1：精簡目前的 git diff
/simplify 審查我目前的 git diff，找出 可以精簡的地方並直接修正
範例 2：指定特定檔案精簡
/simplify 精簡 src/utils/formatter.ts， 這個檔案有很多重複的字串處理邏輯， 看看能不能合併成共用函數
範例 3：搭配程式碼審查後使用
/simplify 剛才修完 /code-reviewer 找到的問題， 請再跑一次確認修正後的程式碼 沒有引入新的複雜度

注意事項

功能正確後才精簡
精簡的前提是程式碼行為已確定。在功能還不穩定或測試尚未通過時執行 /simplify，可能會讓除錯變得更困難。建議養成「先讓它跑，再讓它美」的習慣。

保留刻意的設計決策
某些看起來「重複」的程式碼可能是刻意分開的（例如為了可讀性或未來擴充的彈性）。若 Claude 建議合併時，你認為不妥，可以直接告知原因，Skill 會尊重你的決策。
