程式碼開發 Skill

深度除錯診斷

/diagnose

針對難以復現的 Bug、效能回退與神秘崩潰，採用嚴格的診斷循環： 複現 → 最小化 → 建立假說 → 加入觀測點 → 修正 → 迴歸測試。 適合那種「跑了三遍才觸發一次」的惡夢級 Bug。

Skill 資訊
指令
/diagnose
分類
程式碼開發
適用情境
難以復現的 Bug
診斷流程
6 步驟循環
需要工具
Bash, Read, Grep

適用時機

  • Bug 無法穩定復現，只在特定條件下出現
  • 效能在某次版本更新後突然下降，原因不明
  • 程式在生產環境崩潰，但本機無法重現
  • 已嘗試多種修法但問題仍未解決，需要全面重新診斷
  • Race condition 或並發相關的不穩定問題

六步驟診斷循環

  1. 複現（Reproduce）
    建立穩定的復現步驟，確認 Bug 的觸發條件。若無法穩定復現，先找出是否有共同的環境或狀態條件。
  2. 最小化（Minimise）
    逐步移除不相關的程式碼，建立最小可復現案例（Minimal Reproducible Example），縮小問題範圍。
  3. 建立假說（Hypothesise）
    根據最小案例，提出 2-3 個可能的根本原因假說，以可驗證的方式描述每個假說。
  4. 加入觀測點（Instrument）
    加入 logging、breakpoint 或斷言，針對假說進行實測，確認或排除每個可能原因。
  5. 修正（Fix）
    確認根本原因後實施修正，同時移除診斷過程中加入的臨時觀測程式碼。
  6. 迴歸測試（Regression Test）
    為這個 Bug 新增測試案例，確保相同問題不會在未來版本中再次出現。

使用範例

範例：診斷間歇性崩潰
/diagnose 我的應用每隔幾小時會隨機崩潰， 錯誤訊息是 "Cannot read properties of undefined (reading 'userId')"， 但在開發環境無法重現， 只有在生產環境多用戶並發時才會發生

注意事項

提供越多背景越好
描述 Bug 時，提供錯誤訊息、stack trace、發生頻率、最近的程式碼改動，以及任何你已嘗試過的修法，幫助 Claude 快速鎖定方向。

卡關時換 /codex:rescue
如果 /diagnose 六步驟跑完仍未找到根因，可以試試 /codex:rescue，將問題委派給 Codex 進行更深入的第二輪調查。
