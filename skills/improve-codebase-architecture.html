架構優化分析

/improve-codebase-architecture

掃描整個程式碼庫的架構現況，識別模組邊界問題、循環依賴與過度耦合。 依據程式碼庫既有的技術決策與領域語言提出改善建議，不盲目套用設計模式， 優先考慮實際需求，讓架構演進符合專案的真實脈絡。

適用時機

  • 專案累積超過一定規模後，感覺新功能越來越難加進去時
  • 發現不同模組之間的依賴關係錯綜複雜，難以梳理
  • 修改一個地方意外造成另一個不相關功能出錯（隱性耦合）
  • 接手遺留系統，需要快速理解整體架構全貌與問題所在
  • 規劃大型重構或技術遷移前，需要先摸清現有架構的邊界

使用方式

  1. 執行指令並說明背景
    輸入 /improve-codebase-architecture，可選擇性地說明目前遇到的痛點，例如「模組 A 和 B 一直互相引用」或「新增功能總要改 5 個地方」。
  2. Claude 掃描程式碼庫結構
    Skill 使用 Glob 和 Grep 工具廣泛掃描檔案結構、import 關係與模組邊界，建立整體架構地圖。
  3. 閱讀架構分析報告
    Claude 會輸出架構現況報告，列出識別到的問題（循環依賴、違反層次邊界、過胖的共用模組等），並說明每項問題的影響範圍。
  4. 討論並優先排序重構項目
    與 Claude 討論哪些問題最優先處理，考量改動風險與收益後，訂出分階段的重構計畫。
  5. 逐步執行重構
    依照計畫逐一重構，每個階段結束後可再次執行本 Skill 確認架構是否朝預期方向改善。

使用範例

範例 1：整體架構健診
/improve-codebase-architecture 這個專案用 Node.js 後端 + React 前端， 最近加功能越來越慢，幫我找出 架構上最需要改善的地方
範例 2：針對特定問題深挖
/improve-codebase-architecture src/services/ 裡面的模組彼此互相引用， 我懷疑有循環依賴，請分析並提出 解開依賴的方案
範例 3：重構前評估
/improve-codebase-architecture 我打算把 monolith 拆成 3 個服務， 先幫我分析目前的程式碼邊界在哪， 哪些部分耦合太緊不好拆

注意事項

架構改善不等於套設計模式
本 Skill 的建議基於程式碼庫的實際情況，而非照本宣科套用 Clean Architecture 或 DDD。若你的專案規模不大，過度分層反而是負擔。Claude 會根據實際需求給出務實建議。

大型分析建議提供 CONTEXT.md
若專案根目錄有 CONTEXT.md 或 docs/adr/ 架構決策記錄，Skill 會優先參考這些文件，讓建議更貼近你的技術決策脈絡，避免提出與既有決策衝突的方案。
